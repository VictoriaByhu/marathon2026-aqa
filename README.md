# Green & Tasty — автотести групового pre-order

**Напрям:** Напрям 1, груповий pre-order. Тести перевіряють власний розгорнутий застосунок: Backend з ДЗ #5 (AWS Lambda + API Gateway + DynamoDB) і Frontend з ДЗ #6 (Angular, S3 + CloudFront).

**Підхід:** BDD + Screenplay, на основі наданого фреймворку `aqa/restaurant-aqa-framework`:

- **Reqnroll (Gherkin)** описує сценарії бізнес-мовою;
- **TUnit** запускає тести;
- **Playwright for .NET** працює і з UI, і з API.

Кроки сценаріїв звертаються лише до актора. Актор виконує tasks і відповідає на questions. Page objects і API-клієнти використовуються тільки всередині tasks і questions.

Піраміда тестів відповідає завданню:

- **UI** — основні сценарії: Owner бачить учасників і суми, підтверджує pre-order, видаляє учасника, офіціант бачить замовлення.
- **API** — авторизація й валідація (не-Owner, неавторизований, неіснуюча група, чужий учасник, повторний submit), а також підготовка даних (бронювання, гості, їхні кошики).

## Що покрито

| Рівень | Feature-файл | API | UI |
|---|---|---|---|
| L1 — перегляд учасників | `Features/GroupPreOrderParticipants.feature` | склад і суми учасників, зміна загальної суми, непідтверджений кошик, учасник без страв, порожня група, доступ (інший клієнт, офіціант, гість, неавторизований), неіснуюча група | учасники, страви, кількості, підсумки, загальна сума; позначки «Still choosing» і «No dishes yet»; порожня група |
| L2 — підтвердження | `Features/GroupPreOrderSubmission.feature` | успішне підтвердження з об'єднанням страв, офіціант бачить замовлення, власна сесія Owner, немає підтверджених кошиків, порожній кошик, немає замовлення, неіснуюча група, неіснуюче бронювання, повторний submit, підтвердження не від Owner | підтвердження зі сторінки, кнопка недоступна без підтверджених кошиків |
| L3 — видалення учасника | `Features/GroupPreOrderRemoval.feature` | видалення одного з кількох, учасника з підтвердженим кошиком, останнього учасника; сесію Owner видалити не можна; учасник іншої групи; неіснуючий учасник; видалення не від Owner | видалення зі сторінки; наскрізний сценарій: гості → Owner видаляє одного → підтверджує → офіціант бачить замовлення без видаленого учасника |

| Додаткова функціональність — керування групою | `Features/GroupPreOrderManagement.feature` | Owner змінює кошик гостя (зокрема вже підтверджений), не може спорожнити підтверджений кошик чи додати страву іншого ресторану, бачить меню ресторану; нагадування одному гостю й усім, хто ще обирає; стрічка подій групи, новіші першими; доступ лише для Owner | редагування кошика гостя у вікні на сторінці перегляду; нагадування, яке бачить і Owner, і гість на своїй сторінці; блок Recent activity; кнопка Group pre-order на картці бронювання |

Очікувані значення не захардкоджені. Сценарій веде власну модель кошиків: хто приєднався, що додав, хто підтвердив, кого видалили. Підсумки рахуються з цієї моделі та з цін, які API повертає під час запуску. Тому тести не залежать від конкретних страв і цін у базі.

Страви в сценаріях позначені літерами `A`, `B`, `C`. На початку сценарію під ці літери підставляються доступні страви ресторану, до якого прив'язаний офіціант.

## Структура доданого коду

Нижче перелічено код для групового pre-order. Решта фреймворку лишилася з початкового шаблону.

```
aqa/restaurant-aqa-framework/
├── Features/                       GroupPreOrderParticipants / Submission / Removal
├── StepDefinitions/                GroupPreOrder*StepDefinitions, GroupOrderArgumentTransformations
├── Screenplay/
│   ├── GroupOrders/                модель сценарію: бронювання, кошики гостей, меню, учасники
│   ├── Tasks/GroupOrders/          підготовка ресторану, бронювання, гості, кошики, submit, видалення, дії на сторінках
│   └── Questions/GroupOrders/      що бачить Owner (API і сторінка), замовлення, статус групи, сторінка офіціанта
├── Api/
│   ├── GroupOrdersApi.cs           /guest/groups/..., /group-reservations/.../submit, invite-token, guest-session-id
│   ├── GuestSessionsApi.cs         /guest/sessions/... (приєднання, страви, submit кошика)
│   ├── WaitersApi.cs               локація офіціанта
│   └── Dtos/GroupOrders/
└── Ui/
    ├── GroupPreOrderPage.cs        /reservations/{id}/group-order
    ├── Components/ParticipantCardComponent.cs
    ├── WaiterPreOrderPage.cs       /waiter-pre-order
    ├── StorefrontSession.cs
    └── LocatorWaits.cs
```

Локатори на сторінках, за пріоритетом:

1. роль + доступне ім'я: заголовки карток, кнопки `Remove <ім'я>`, діалоги `Remove Guest` і `Submit Pre-Order`;
2. стабільні класи компонентів.

Позиційних селекторів і `sleep` немає. Очікування робить Playwright, а питання, що читають сторінку, дочікуються потрібного стану самі.

## Тестові дані

Кожен сценарій створює все, що йому потрібно:

1. Офіціант входить у систему. За його токеном визначається локація, з неї читається меню.
2. Для сценарію створюється **окремий стіл** у цій локації, тому бронювання паралельних сценаріїв не перетинаються.
3. Реєструється **новий клієнт-Owner** з унікальним email `aqa.sample.<guid>@example.com` та ім'ям із префіксом `AQA-Sample-`.
4. Owner бронює стіл на `сьогодні + 14…74 дні`, 10:00 UTC; друге бронювання в тому самому сценарії — на 4 години пізніше. Час завжди рахується від поточного моменту.
5. Гості приєднуються за справжнім запрошенням (`invite-token` → `guest/invites/{token}`) і наповнюють кошики через гостьовий API.

Після сценарію все прибирається у зворотному порядку: бронювання скасовується від імені Owner, після цього стіл видаляється від імені офіціанта. Сценарії не залежать один від одного й від порядку запуску, тому можуть виконуватися паралельно.

## Налаштування

Потрібні .NET 10 SDK і розгорнуті Backend та Frontend.

```bash
cd aqa/restaurant-aqa-framework
cp .env.example .env
```

У `.env` заповнити:

| Змінна | Значення |
|---|---|
| `UI_URL` | адреса фронтенду (CloudFront) |
| `API_URL` | адреса API разом зі stage, наприклад `https://<id>.execute-api.<region>.amazonaws.com/develop` |
| `WAITER_USERNAME`, `WAITER_PASSWORD` | обліковий запис офіціанта: користувач Cognito у групі `Waiter` із записом у таблиці `Waiters`, прив'язаним до локації з принаймні двома доступними стравами |

`.env` не комітиться. Паролів і адрес у репозиторії немає.

## Запуск

```bash
cd aqa/restaurant-aqa-framework
dotnet build
dotnet run --no-build -- --report-trx
```

Підмножина за тегом:

```bash
dotnet run --no-build -- --treenode-filter "/*/*/*/*[Category=level-1]"
dotnet run --no-build -- --treenode-filter "/*/*/*/*[Category=api]"
dotnet run --no-build -- --treenode-filter "/*/*/*/*[Category=smoke]"
```

| Тег | Що відбирає |
|---|---|
| `@level-1`, `@level-2`, `@level-3` | рівень завдання (тег стоїть на feature) |
| `@api`, `@ui` | рівень піраміди; тег також визначає, чи запускається браузер |
| `@smoke` | основні позитивні сценарії кожного рівня |
| `@negative` | негативні сценарії |
| `@security` | перевірки доступу (не-Owner, гість, неавторизований) |
| `@e2e` | наскрізний сценарій від кошиків гостей до офіціанта |
| `@extra` | додаткова функціональність: редагування кошика гостя, нагадування, стрічка подій, перехід з картки бронювання |

## Звіти

Усе, що створює запуск, лежить у `aqa/restaurant-aqa-framework/TestResults/`:

- `*-report.html` і `*.trx` — звіт TUnit;
- `reqnroll/reqnroll_report.html` — звіт Reqnroll зі сценаріями й кроками;
- `traces/*.zip` — Playwright trace для кожного UI-сценарію, що впав: скриншоти, DOM, мережа, консоль. Відкрити: `npx playwright show-trace <файл>.zip`.

## CI

| Workflow | Коли запускається | Що робить |
|---|---|---|
| `.github/workflows/aqa-quality.yml` | push і pull request у `main` | формат, збірка (попередження — помилки), Gherkin lint, перевірка, що всі кроки зв'язані |
| `.github/workflows/aqa-tests.yml` | push у `main` і вручну (Actions → AQA Tests → Run workflow) | запуск сценаріїв проти розгорнутого застосунку |

Для ручного запуску можна вибрати `scope`: `all`, `api`, `ui`, `smoke`, `level-1`, `level-2`, `level-3`, `extra`. Також можна задати власний фільтр.

Впалий тест не зупиняє пайплайн. Звіти TUnit і Reqnroll, TRX і Playwright traces завжди публікуються як артефакти запуску. Короткий підсумок (скільки пройшло, скільки впало, список впалих сценаріїв) показується на сторінці запуску. Сама job позначається червоною, якщо хоч один тест упав.

Налаштування в **Settings → Secrets and variables → Actions**:

- **Variables:** `AQA_UI_URL`, `AQA_API_URL`
- **Secrets:** `AQA_WAITER_USERNAME`, `AQA_WAITER_PASSWORD`

## Обрана поведінка для випадків, не визначених у ДЗ

| Випадок | Поведінка, яку перевіряють тести |
|---|---|
| Список учасників або submit від іншого клієнта чи офіціанта | `403`, дані групи не змінюються, група лишається в статусі `Open` |
| Запит без входу в систему або з гостьовим токеном замість токена Cognito | `401` від авторизатора API Gateway |
| Повторний submit уже підтвердженої групи | `400` з повідомленням `Group reservation was submitted.`; склад замовлення не змінюється, страви не дублюються |
| Група, до якої ніхто не приєднався | `participants: []`, `total: 0` |
| Видалення останнього гостя | дозволено; повертається оновлений знімок групи з `participants: []` і `total: 0` |
| Видалення учасника, який уже підтвердив кошик | дозволено; його страви більше не входять у суму й не потраплять у замовлення |
| Видалення сесії самого Owner | `400` з повідомленням `Owner session cannot be removed from the group.` |
| Учасник іншої групи | `400` з повідомленням `Guest session does not belong to this group reservation.`; учасник лишається у своїй групі |
| Неіснуючий учасник, група або бронювання | `404` |
| Немає замовлення Owner, до якого додаються страви | `400` з повідомленням `Order for reservation <id> was not found.` |
| Сесія Owner у групі | створюється під час першого запиту `guest-session-id`, у списку стоїть першою з типом `Owner` та ім'ям Owner. Власні страви Owner додає звичайним pre-order до бронювання; під час submit страви гостей додаються до цього замовлення |
| Загальна сума | API `total` — сума підсумків усіх учасників, зокрема тих, хто ще обирає. Grand Total на сторінці — сума лише підтверджених кошиків, тобто того, що піде в замовлення |

### Додаткова функціональність

| Випадок | Поведінка, яку перевіряють тести |
|---|---|
| Owner змінює кошик гостя | кошик замінюється повністю, однакові страви об'єднуються; гість, який уже підтвердив кошик, лишається підтвердженим, і в замовлення ресторану потрапляє виправлений склад |
| Підтверджений кошик стає порожнім | `400` з повідомленням `A submitted cart cannot be left empty. Remove the guest instead.` |
| Страва не з меню цього ресторану | `400`, повідомлення містить `is not on the menu of this restaurant` |
| Нагадування гостю, який уже підтвердив кошик | `400` з повідомленням `This guest has already submitted the cart.` |
| Нагадування всім | отримують лише гості, які ще обирають; Owner і гості з підтвердженим кошиком — ні; гість бачить нагадування на своїй сторінці |
| Стрічка подій | до 50 останніх подій, новіші першими: приєднання, додані й прибрані страви, підтвердження кошика, видалення гостя, зміна замовлення Owner, нагадування, відправлення групи |
| Редагування, нагадування, меню й стрічка не від Owner | `403` для іншого клієнта й офіціанта, `401` без входу або з гостьовим токеном |

### Умова «у підтверджених кошиках немає жодної страви»

Через публічний API цю умову створити неможливо. Порожній кошик підтвердити не можна (`400`, `The cart is empty`), а підтверджений кошик більше не змінюється. Тому замість неї окремий сценарій перевіряє саме це обмеження. Гілку коду, яка повертає `Submitted guest sessions do not contain any dishes.`, покривають unit-тести бекенду з ДЗ #5.
